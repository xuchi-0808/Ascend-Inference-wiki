## 实验 3：关 cudagraph（验证 mc2_mask + cudagraph 交互，方向 2）

**目的**：`mc2_mask` 是进程级全局 buffer，每 forward in-place 改写 `[:num_actual_tokens]=True`。如果 cudagraph 把这个写入 capture 进了捕获图，replay 时 mask 不会按实际 token 数更新 → 多并发下 token 数变化 → mask 错 → 有效 token 被当 padding 丢弃。关 cudagraph 验证这一假设。

**前提**：先回退实验 2 的改动（恢复 `fused_moe.py:282` 的 `MoECommType.MC2,`），同时确认实验 1 已回退（MC2 恢复工作）。

### 改动（纯参数，两个节点 serve 命令都加）

在 Node 0 和 Node 1 的 `vllm serve` 命令中**加一行**：

```bash
    --compilation-config '{"cudagraph_mode": "NONE"}'
```

**示例**（Node 0，加在 `--safetensors-load-strategy prefetch` 之前）：

```bash
vllm serve "/home/data/Qwen3-235B-A22B" \
```

| 结果 | 含义 | 下一步 |

## 实验 1-3 综合结论（2026-06-17）

**根因**：cudagraph + MC2 路径中 **Qwen3-A22B 特有的操作**被 capture。

实验链：（1）ALLGATHER 恢复 → MC2 路径是根因；（2）关 cudagraph 恢复 → cudagraph 是必要条件。但 GLM-5.1 和 Kimi-K2.5 同样走 A2 MC2+cudagraph 且通过，排除了通用 MC2 mask 问题。根因在 Qwen3 特有的 logic（fusion_ops expert selector `npu_moe_gating_top_k`、0-shared expert 的 `forward_impl` 分支）。

### 实验矩阵

| # | 改动 | 改法 | 结果 | 含义 |
|---|------|------|------|------|
| 1 | ALLGATHER 绕开 MC2 | `ascend_forward_context.py:278` → `if False:` | ✅ | MC2 是根因 |
| 2 | 恢复 TP all-reduce | `fused_moe.py:282` 删 `MoECommType.MC2,` | ❌ | 无关 |
| 3 | 关 cudagraph | `--compilation-config '{"cudagraph_mode": "NONE"}'` | ✅ | cudagraph 是必要条件 |

### 推理链

```text
7fd2cede (runner DefaultMoERunner→MoERunner)
  → cudagraph capture 范围变化
    → mc2_mask in-place 写入被 capture
      → replay 时 mask 保持旧值（token 数不匹配）
        → 有效 token 被当 padding 丢弃
          → 多并发乱码（单请求 batch 小 mask 碰巧对）
```

### 依赖环境排除

| 组件 | 5/9（成功） | 5/10（失败） | 结论 |
|------|-----|------|------|
| CANN | 8.5.1 | 8.5.1 | 相同 |
| triton-ascend | 3.2.0 | 3.2.0 | 相同 |
| npu-smi | 25.5.2 | 25.5.2 | 相同 |
| Post-install | 无 | 无 | 都没做 |

### 修复方向

在 `ascend_forward_context.py` 中将 `mc2_mask` 的 in-place 写入标记为 cudagraph-unsafe，或在 `AscendMoERunner` 初始化逻辑中确保该操作不被 capture。
