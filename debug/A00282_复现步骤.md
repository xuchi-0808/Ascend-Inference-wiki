# A00282 — 绿区 E5 验证手册

> 2026-06-21 重构。根因在 A2 已验证（E1/E3 绿区通过），A3 无法复现（E4 已放弃）。
> 唯一待跑：E5（mc2_mask tensor 比较修复）。
> 协作模式：AI 写文档，用户在内网绿区（`80.48.37.120/121`）手操。

## TL;DR

- **根因**：`mc2_mask[:num_actual_tokens]=True`（`ascend_forward_context.py:185`）的 in-place 写入被 cudagraph capture，replay 时 `num_actual_tokens` 保持 capture 时的值 → mask stale → 有效 token 被当 padding 丢弃 → MC2 dispatch 输出错乱
- **已验证**：E1（ALLGATHER）✅ + E3（关 cudagraph）✅ → MC2 + cudagraph 是根因
- **下一步**：E5 改 in-place 为 tensor 比较 → 验证精度恢复
- **关键**：Qwen3-235B-A22B 是 0-shared experts，100% 依赖 MC2；GLM/Kimi 有 shared expert 补偿不显性失败；A3 走 FUSED_MC2 独立路径不受影响

## E5：mc2_mask tensor 比较修复（当前重点）

### 改什么

文件：`vllm_ascend/ascend_forward_context.py:182-187`

修改前：

```python
reserved_mc2_mask = get_mc2_mask()
if reserved_mc2_mask is not None:
    mc2_mask = reserved_mc2_mask[: forward_context.padded_num_tokens]
    mc2_mask[:num_actual_tokens] = True
    mc2_mask[num_actual_tokens:] = False
    forward_context.mc2_mask = mc2_mask
```

修改后：

```python
reserved_mc2_mask = get_mc2_mask()
if reserved_mc2_mask is not None:
    # A00282-fix: avoid in-place writes with dynamic Python slice indices.
    # Under cudagraph, mc2_mask[:num_actual_tokens]=True captures the
    # capture-time num_actual_tokens value; on replay the stale mask
    # misclassifies real tokens as padding, causing MC2 dispatch to
    # drop them. Fix: build mask via tensor comparison so
    # num_actual_tokens flows through as a runtime device value.
    padded = forward_context.padded_num_tokens
    device = reserved_mc2_mask.device
    positions = torch.arange(padded, device=device)
    num_actual_tensor = torch.tensor(num_actual_tokens, device=device)
    forward_context.mc2_mask = positions < num_actual_tensor
```

### 原理

| 操作 | cudagraph 行为 | 问题？ |
|------|---------------|--------|
| `mc2_mask[:N] = True`（旧） | capture 时 N 被 Python int 固化，replay 用旧 N | **是** |
| `positions < num_actual_tensor`（新） | `num_actual_tensor` 是 device tensor，replay 时读当前值 | **否** |

`torch.arange` 和 `<` 都是 tensor op，被 capture 进图。但 `num_actual_tensor` 的值在每次 Python `forward()` 执行时重新创建（`torch.tensor(num_actual_tokens, ...)`），Python 层的 `num_actual_tokens` 变量每次取当前实际值。cudagraph replay 前会把输入 tensor 更新到当前值，mask 因此正确。

## 根因分析

### 推理链

```text
vllm MoE refactor（#35782 / #35949 / #40560）改变了 MoERunner.forward() 的 scope
  → mc2_mask 的 in-place 写入 mc2_mask[:num_actual_tokens]=True 落入 cudagraph capture 范围
    → replay 时 num_actual_tokens 是 capture 时的值（Python int 不更新）
      → mask 标记错误（真实 token 被标 False，当 padding 丢弃）
        → MC2 dispatch 丢弃真实 token → combine 输出错乱
          → Qwen3 (0 shared) 全错；GLM/Kimi (有 shared) 被 shared expert 补偿
```

### 为什么 GLM-5.1 / Kimi-K2.5 不显性失败

三个模型都走相同的 MC2 + cudagraph + mc2_mask 路径，mask 问题对三者同等生效。但：

- **GLM/Kimi 有 shared experts**：最终输出 = `shared_output + fused_output`。shared expert 对所有 token 做 dense 计算，提供正确"基座信号"。即使 fused_output 部分错乱，shared output 的正确性足以让 accuracy 维持在阈值以上。
- **Qwen3-A22B 是 0 shared experts**：最终输出 = `fused_output`（纯 MC2 结果）。MC2 错乱 = 输出 100% 错乱 → accuracy 归零。

不是"GLM/Kimi 不受影响"，而是"shared expert 补偿了 MC2 的错误"。

### 为什么 A3 不显性失败

A3 的 `select_moe_comm_method` 走 A3 分支，优先选 **FUSED_MC2**（`FusedMC2CommImpl` + `dispatch_ffn_combine` 算子），完全不走 `TokenDispatcherWithMC2`，也不碰 `mc2_mask`。是独立代码路径。E4 实验确认 A3 单机强制 MC2 也不复现（32 并发精度正常），猜测 A3 HCCS 对 mask 错误不敏感或新代码改了 capture 范围。

### 依赖环境排除

5/9 成功版与 5/10 失败版的 CANN（8.5.1）、triton-ascend（3.2.0）、npu-smi（25.5.2）完全一致，非环境因素。

## 注意事项

- 两个节点之间需互通 **8080**（API）和 **13389**（DP RPC）端口
- 权重路径：Node 0 = `/home/data/Qwen3-235B-A22B`，Node 1 = `/mnt/weight/Qwen3-235B-A22B`
- `--async-scheduling` 对齐 5/9 成功日志（A2 nightly 一直使用）
- `--safetensors-load-strategy prefetch` 非 5/9 原始参数，仅加速权重加载；老版本若报 `unrecognized arguments` 可去掉
- **CWD 陷阱**：起 serve 前不要 `cd /vllm-workspace`，否则 `vllm` 被 Python 当相对目录解析 → `ImportError: cannot import name 'SamplingParams'`。改用 `cd /root`
- **NPU 清理**：`npu-smi info` 看卡上 Process id → `kill -9 <pid>`。docker stop 容器后 HBM 自动释放
- **绿区用 6/10 之后版本**：默认 `cudagraph_mode=FULL_AND_PIECEWISE`（O2），capture_sizes 有 19 个（`[1,2,4,...,128]`），拉起 capture 阶段比 5/9 版本（3 个 size）久一些，不影响正确性
