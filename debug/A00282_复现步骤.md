# A00282 — 绿区诊断打点手册

> 2026-06-22 更新。升级 PTA 后使用 `print_npugraph_tensor` 做图内诊断。
> 已排除：mc2_mask stale（普通 print 证明不在 capture scope）、prefix-caching、量化、decode cudagraph。
> 新可疑点：`self.num_tokens` 实例属性跨 prepare→finalize 传递，在 capture scope 内可能 stale。
> 协作模式：AI 写文档，用户在内网绿区（`80.48.37.120/121`）手操。

## TL;DR

- **已排除的方向**：mc2_mask stale（不在 capture scope）、prefix-caching、量化（BF16/W8A8 都挂）、decode cudagraph（FULL_DECODE_ONLY 不恢复）、moe_forward vs moe_forward_shared（MC2 核心逻辑共享）
- **新可疑点**：`PrepareAndFinalizeWithMC2.prepare` 里设置的 `self.num_tokens`（Python int 实例属性），在 `finalize` 里用于 slice。如果 prepare/finalize 都在 capture scope 内，replay 时 `self.num_tokens` 可能 stale
- **触发条件**：只有全 NONE（E3）恢复精度；单并发对、多并发错
- **关键配置对比**：nightly A2 里只有 Qwen3 无 speculative decode，其他模型（DeepSeek-R1/GLM-5.1/Kimi-K2.5）都有 speculative
- **下一步**：升级 PTA 后用 `print_npugraph_tensor` 在 MC2 路径关键节点打点，定位哪个环节的 tensor 值异常

## E7：图内诊断 — print_npugraph_tensor（当前重点）

### 目的

在 MC2 路径的关键节点加 `torch_npu.print_npugraph_tensor`，拿到 replay 时的真实 tensor 值，定位哪个环节输出了问题。

### 前提

升级 PTA 到支持 `print_npugraph_tensor` 的版本。这个接口是 tensor 级操作，会被 aclgraph 捕获，**replay 时也能触发打印**——比普通 print 可靠（普通 print 在 capture scope 内 replay 时不执行）。

## 根因分析

### 已排除的方向

| 方向 | 排除依据 |
|------|---------|
| mc2_mask stale | 普通 print 证明 mask 设置在 `__enter__`（capture scope 外），每次正确更新 |
| prefix-caching | 默认 + 关 prefix-caching 不恢复 |
| 量化（BF16 vs W8A8） | w8a8 一样挂 |
| decode cudagraph | FULL_DECODE_ONLY 不恢复 |
| MC2 dispatch 参数差异 | 所有 A2 模型走相同 uniform 模式（global_bs=0），参数一致 |
| moe_forward vs moe_forward_shared | 两者共享 layer.forward_impl 的 MC2 核心逻辑 |

### 当前可疑点：self.num_tokens 实例属性

`PrepareAndFinalizeWithMC2.prepare`（`prepare_finalize.py`）设置：

```python
self.num_tokens, _ = hidden_states.shape   # Python int
```

`PrepareAndFinalizeWithAll2All.finalize` 使用：

```python
if self.num_tokens < hidden_states.shape[0]:
    hidden_states = hidden_states[: self.num_tokens]   # 用实例属性做 slice
```

如果 prepare 和 finalize 都在 cudagraph capture scope 内：

- capture 时：prepare 执行 → `self.num_tokens` 设为 capture_size
- replay 时：prepare 不执行 → `self.num_tokens` 保持上一次的值
- finalize 用陈旧的 `self.num_tokens` 做 slice → 输出错乱

**能解释的观察**：

- 单并发对（始终同一个 capture_size，num_tokens 一致）
- 多并发错（不同 size 交替，num_tokens 可能陈旧）
- 只有全 NONE 恢复（prepare 每次 Python 执行，num_tokens 正确）

**待 E7 确认**：用 `print_npugraph_tensor` 对比 prepare 和 finalize 的 num_tokens 值。

### nightly A2 配置对比

| 配置项 | Qwen3-235B-A22B | DeepSeek-R1 | GLM-5.1 | Kimi-K2.5 |
|--------|:-:|:-:|:-:|:-:|
| cudagraph_mode | 默认（PIECEWISE/FULL_AND_PIECEWISE） | FULL_DECODE_ONLY | FULL_DECODE_ONLY | FULL_DECODE_ONLY |
| prefix-caching | 开 | 关 | 关 | 关 |
| **speculative** | **无** | **mtp** | **mtp** | **eagle3** |
| quantization | BF16/W8A8 | W8A8 | W8A8 | W4A8 |

**关键差异**：Qwen3 是唯一无 speculative decode 的模型。speculative 可能改变了 decode 的 batch 结构，间接影响 cudagraph 的 capture/replay 行为。

### 间接证据（E1/E3）

| 实验 | 改动 | 结果 | 说明 |
|------|------|------|------|
| E1 | 绕开 MC2 走 ALLGATHER | ✅ 恢复 | MC2 路径有问题 |
| E3 | 关 cudagraph | ✅ 恢复 | cudagraph 是必要条件 |

### 为什么 GLM-5.1 / Kimi-K2.5 不显性失败

待确认。可能原因：

1. speculative decode 改变了 batch 结构，避免了不同 capture_size 的交替
2. 有 shared experts 补偿了 routed_out 的错误
3. 走了不同的代码路径（待排查）

### 依赖环境排除

5/9 成功版与 5/10 失败版的 CANN（8.5.1）、triton-ascend（3.2.0）、npu-smi（25.5.2）完全一致，非环境因素。

## 注意事项

- 两个节点之间需互通 **8080**（API）和 **13389**（DP RPC）端口
- 权重路径：Node 0 = `/home/data/Qwen3-235B-A22B`，Node 1 = `/mnt/weight/Qwen3-235B-A22B`
- `--async-scheduling` 对齐 5/9 成功日志（A2 nightly 一直使用）
- `--safetensors-load-strategy prefetch` 非 5/9 原始参数，仅加速权重加载；老版本若报 `unrecognized arguments` 可去掉
- **CWD 陷阱**：起 serve 前不要 `cd /vllm-workspace`，否则 `vllm` 被 Python 当相对目录解析 → `ImportError: cannot import name 'SamplingParams'`。改用 `cd /root`
- **NPU 清理**：`npu-smi info` 看卡上 Process id → `kill -9 <pid>`。docker stop 容器后 HBM 自动释放
- **绿区用 6/10 之后版本**：默认 `cudagraph_mode=FULL_AND_PIECEWISE`（O2），capture_sizes 有 19 个（`[1,2,4,...,128]`），拉起 capture 阶段比 5/9 版本（3 个 size）久一些，不影响正确性
- **改代码后确认生效**：绿区直接改 site-packages 里的文件即可（不用 `pip install -e .`），但改完要确认实际加载路径：`python3 -c "import vllm_ascend.ascend_forward_context as m; print(m.__file__)"` 应指向你改的文件
