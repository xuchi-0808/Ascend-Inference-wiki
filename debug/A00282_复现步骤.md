## E6：诊断打点 — 确认 mc2_mask 是否 stale（当前重点）

### 目的

拿到直接数据回答一个问题：**cudagraph replay 时，mc2_mask 的值是固定的还是动态更新的？**

- 固定 → mask stale 假说成立，这就是根因
- 动态 → 排除 mc2_mask，排查 MC2 路径其他环节

### 为什么用 `print_npugraph_tensor` 而不是普通 print

cudagraph replay 时 **Python 代码不执行**——只有 tensor 操作被回放。所以 `print()` / `logger.info()` 在 replay 时不会触发。

`torch_npu.print_npugraph_tensor` 是一个 **tensor 级操作**，会被 aclgraph 捕获进图。replay 时它跟着回放，能打印出 tensor 当前的真实值。这是 PTA 专门为"图内打印"设计的接口。

### 打印什么

`mc2_mask.sum()` —— mask 里 True 的个数 = 实际 token 数。

一个数值就够判断：stale 则固定不变，正常则随 batch 变化。不需要打印整个 mask（太长）。

### 改什么

文件：`vllm_ascend/ascend_forward_context.py`，在 mc2_mask 设置完之后（约 line 187 之后）**加一行**。**不改原有逻辑**。

修改前（原有代码，不动）：

```python
            reserved_mc2_mask = get_mc2_mask()
            if reserved_mc2_mask is not None:
                mc2_mask = reserved_mc2_mask[: forward_context.padded_num_tokens]
                mc2_mask[:num_actual_tokens] = True
                mc2_mask[num_actual_tokens:] = False
                forward_context.mc2_mask = mc2_mask
```

修改后（只加最后 4 行打印）：

```python
            reserved_mc2_mask = get_mc2_mask()
            if reserved_mc2_mask is not None:
                mc2_mask = reserved_mc2_mask[: forward_context.padded_num_tokens]
                mc2_mask[:num_actual_tokens] = True
                mc2_mask[num_actual_tokens:] = False
                forward_context.mc2_mask = mc2_mask
                # A00282-diag: 图内打印 mask sum，capture + replay 都能看到
                import torch_npu
                torch_npu.print_npugraph_tensor(
                    mc2_mask.sum().unsqueeze(0).to(torch.int32),
                    tensor_name="mc2_mask_sum",
                )
```

> `mc2_mask.sum()` 返回 0-dim tensor，`unsqueeze(0)` 转成 1-dim 满足接口要求。打印的值 = mask 里 True 的个数 = 实际 token 数。

## 根因分析

### 怀疑的问题（待 E6 确认）

mc2_mask 的 in-place 写入 `mc2_mask[:num_actual_tokens]=True` 在 cudagraph capture 时，`num_actual_tokens`（Python int）被固化。replay 时：

```text
replay 时图里用的是 capture 时的 num_actual_tokens（旧值）
  → mask 标记错误（真实 token 被标 False，当 padding 丢弃）
    → MC2 dispatch 丢弃真实 token → combine 输出错乱
      → Qwen3 (0 shared) 全错；GLM/Kimi (有 shared) 被 shared expert 补偿
```

### 间接证据（E1/E3）

| 实验 | 改动 | 结果 | 说明 |
|------|------|------|------|
| E1 | 绕开 MC2 走 ALLGATHER | ✅ 恢复 | MC2 路径有问题 |
| E3 | 关 cudagraph | ✅ 恢复 | cudagraph 是必要条件 |

两个结合 → MC2 + cudagraph 交互是根因。但具体是不是 mc2_mask stale，需要 E6 直接验证。

### 为什么 GLM-5.1 / Kimi-K2.5 不显性失败

三个模型都走相同的 MC2 + cudagraph + mc2_mask 路径，mask 问题对三者同等生效。但：

- **GLM/Kimi 有 shared experts**：最终输出 = `shared_output + fused_output`。shared expert 对所有 token 做 dense 计算，提供正确"基座信号"。即使 fused_output 部分错乱，shared output 的正确性足以让 accuracy 维持在阈值以上。
- **Qwen3-A22B 是 0 shared experts**：最终输出 = `fused_output`（纯 MC2 结果）。MC2 错乱 = 输出 100% 错乱 → accuracy 归零。

不是"GLM/Kimi 不受影响"，而是"shared expert 补偿了 MC2 的错误"。

### 为什么 A3 不显性失败

A3 的 `select_moe_comm_method` 走 A3 分支，优先选 **FUSED_MC2**（`FusedMC2CommImpl` + `dispatch_ffn_combine` 算子），完全不走 `TokenDispatcherWithMC2`，也不碰 `mc2_mask`。是独立代码路径。E4 实验确认 A3 单机强制 MC2 也不复现（32 并发精度正常），猜测 A3 HCCS 对 mask 错误不敏感或新代码改了 capture 范围。

### 依赖环境排除

5/9 成功版与 5/10 失败版的 CANN（8.5.1）、triton-ascend（3.2.0）、npu-smi（25.5.2）完全一致，非环境因素。

## 注意事项

- 两个节点之间需互通 **8080**（API）和 **13389**（DP RPC）端口
- 权重路径：Node 0 = `/home/data/Qwen3-235B-A22B`，Node 1 = `/mnt/weight/Qwen3-235B-A22B`
- `--async-scheduling` 对齐 5/9 成功日志（A2 nightly 一直使用）
- `--safetensors-load-strategy prefetch` 非 5/9 原始参数，仅加速权重加载；老版本若报 `unrecognized arguments` 可去掉
- **CWD 陷阱**：起 serve 前不要 `cd /vllm-workspace`，否则 `vllm` 被 Python 当相对目录解析 → `ImportError: cannot import name 'SamplingParams'`。改用 `cd /root`
- **NPU 清理**：`npu-smi info` 看卡上 Process id → `kill -9 <pid>`。docker stop 容器后 HBM 自动释放
- **绿区用 6/10 之后版本**：默认 `cudagraph_mode=FULL_AND_PIECEWISE`（O2），capture_sizes 有 19 个（`[1,2,4,...,128]`），拉起 capture 阶段比 5/9 版本（3 个 size）久一些，不影响正确性
- **改代码后确认生效**：绿区直接改 site-packages 里的文件即可（不用 `pip install -e .`），但改完要确认实际加载路径：`python3 -c "import vllm_ascend.ascend_forward_context as m; print(m.__file__)"` 应指向你改的文件
